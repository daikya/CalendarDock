# CalendarDock データベース仕様

作成日: 2026-10-09  
対象: DB構造バージョン3（`PRAGMA user_version = 3`）

本書は、この開発セッションで提示し、ユーザー環境でテスト・実機確認された実装に基づく。ユーザーPCのソースコードやDBを直接取得した仕様書ではない。構造変更時は本書も更新する。

## 1. 保存方式と対象範囲

- SQLCipherで暗号化したSQLite DBに、予定・CSV取込履歴・アプリ識別情報を保存する。
- DBを開く際にパスワードを入力する。パスワード自体をテーブルや設定JSONへ保存する処理はない。
- 通常利用の新規作成は`create_calendar_database()`を使用し、バージョン3まで構造を整える。
- `create_database()`はバージョン1の基礎DBを作成する。更新処理のテスト等でも使用している。
- 通知機能と繰り返し規則の管理は対象外。CSVの各行を一つの予定として取り込む。
- 元CSV内のアラーム項目は移行元情報として残すが、通知には使用しない。

DB保存場所は選択可能。開発時の実データは`CalendarDock\data\calendar.db`へ取り込んだ。位置・サイズの設定はDB外の`%LOCALAPPDATA%\CalendarDock\window_settings.json`に保存する。

## 2. テーブルと関連

| テーブル | 用途 | 関連 |
|---|---|---|
| `app_metadata` | アプリ識別情報 | 独立した管理テーブル |
| `import_batches` | CSVを取り込んだ単位で履歴を保持 | 一つの履歴に複数の予定が対応 |
| `events` | 現在の予定内容と、移行元情報を保持 | `import_batch_id`から取込履歴を参照 |

CSV由来の予定は`import_batches.id`と関連付く。CalendarDockで新規登録した予定は取込履歴を持たない。削除済みになっても関連は維持する。

## 3. app_metadata

| 項目 | SQLite型 | 制約・初期値 | 意味 |
|---|---|---|---|
| `key` | TEXT | PRIMARY KEY | 管理情報の名前 |
| `value` | TEXT | NOT NULL | 管理情報の値 |

現在、通常利用で保存する管理情報は`key = 'application'`、`value = 'CalendarDock'`。予定件数・パスワード・ウィンドウ設定は、このテーブルには保存しない。

`key`のDDLは`TEXT PRIMARY KEY`で、明示的な`NOT NULL`は付けていない。通常処理では固定の文字列キーを使用する。

## 4. import_batches

| 項目 | SQLite型 | NULL | 制約・初期値 | 意味 |
|---|---|---|---|---|
| `id` | INTEGER | 自動採番 | PRIMARY KEY | CSV取込履歴のID |
| `source_name` | TEXT | 不可 | NOT NULL | 元CSVのファイル名。フルパスは保存しない |
| `source_fingerprint` | TEXT | 不可 | NOT NULL、UNIQUE | 解析後の元データから生成したSHA-256の16進文字列 |
| `imported_at` | TEXT | 不可 | NOT NULL | 取込日時。UTC、秒単位のISO形式 |
| `event_count` | INTEGER | 不可 | NOT NULL、0以上 | その取込で保存した予定件数 |

`imported_at`の例: `2026-10-09T07:30:00+00:00`。予定の日時と違い、UTCオフセットを含む。

`event_count`は取込当時の件数であり、削除済み除外後の件数ではない。新規登録した予定も含まない。

### 同じCSVの再取込防止

元の各行の全項目を、キーを並べ替えたJSONへ変換し、それらを行順にまとめたJSONのUTF-8バイト列からSHA-256を計算する。

- ファイル名だけ変更しても、同一データなら再取込を拒否する。
- CP932とUTF-8の違いだけなら、解析後の項目値が同一である限り再取込を拒否する。
- CSVのレコード区切りの違いは指紋に影響しない。内容フィールド内の改行など、値そのものが違えば別データとなる。
- 行の並びや項目値を変更したCSVは別の取込となる。
- 予定単位の重複照合・更新は行わない。別CSV間の同じ予定は重複保存され得る。
- 取り込んだ予定を編集・削除しても、取込履歴の指紋は変わらない。同じCSVを再取込して削除済み予定を復活させる動作はしない。

## 5. events

| 項目 | SQLite型 | NULL | 制約・初期値 | 意味 |
|---|---|---|---|---|
| `id` | INTEGER | 自動採番 | PRIMARY KEY | 予定ID。一覧・詳細・編集・削除の識別に使用 |
| `subject` | TEXT | 不可 | NOT NULL | 件名。空文字は許容 |
| `starts_at` | TEXT | 不可 | NOT NULL | 開始日時。タイムゾーンなし、秒単位のISO形式 |
| `ends_at` | TEXT | 不可 | NOT NULL | 終了日時。同上 |
| `all_day` | INTEGER | 不可 | NOT NULL、0または1 | 0: 時刻指定、1: 終日 |
| `location` | TEXT | 不可 | NOT NULL | 場所。未入力は空文字 |
| `body` | TEXT | 不可 | NOT NULL | 内容。日本語・複数行を保持 |
| `categories` | TEXT | 不可 | NOT NULL | 分類。文字列として保存し、分類ごとのテーブルは作らない |
| `source_row` | INTEGER | 可 | 値がある場合は2以上 | 元CSVのレコード番号。ヘッダーを1とする |
| `source_fields_json` | TEXT | 可 | 移行元3項目の整合性制約 | 元CSVの全項目を文字列値のJSONとして保存 |
| `import_batch_id` | INTEGER | 可 | FOREIGN KEY | `import_batches.id`を参照 |
| `is_deleted` | INTEGER | 不可 | NOT NULL、DEFAULT 0、0または1 | 0: 通常、1: 削除済み |

開始・終了の例: `2026-10-09T09:00:00`。日本時間の入力をUTCへ変換する処理はなく、CSVや画面で指定した現地日時を保持する。

### キー・制約・索引

- `id`は`INTEGER PRIMARY KEY`。`AUTOINCREMENT`指定はない。通常の削除は物理削除しないため、既存の予定IDを保持する。
- `UNIQUE (import_batch_id, source_row)`で、同じ取込内の同じレコード番号の重複保存を防止する。
- 元CSV内で内容が同じ複数行は、レコード番号が異なるため両方保存する。
- 移行元3項目は、すべてNULL、またはすべて値ありでなければならない。
- 新規予定では移行元3項目をすべてNULLにする。
- 索引`idx_events_starts_at`を`starts_at`に設定している。
- 外部キーの削除連鎖（`ON DELETE CASCADE`）は指定していない。

`starts_at`・`ends_at`の形式や前後関係はアプリ側で検証する。DB自体に日時形式・前後関係のCHECK制約はない。JSONの構文もDBのCHECKでは検証しない。

## 6. Outlook CSVの22項目との対応

全22項目を、元の列名・文字列値のまま`source_fields_json`に保持する。以下の「通常項目」は、現在の予定を表示・編集するための保存先を指す。

| Outlook CSV項目 | 通常項目への反映 | 移行後の扱い |
|---|---|---|
| 件名 | `subject` | 表示・編集・検索対象 |
| 開始日 | `starts_at`の日付部分 | 開始時刻と合わせて変換 |
| 開始時刻 | `starts_at`の時刻部分 | 開始日と合わせて変換 |
| 終了日 | `ends_at`の日付部分 | 終了時刻と合わせて変換 |
| 終了時刻 | `ends_at`の時刻部分 | 終了日と合わせて変換 |
| 終日イベント | `all_day` | `True`/`False`を1/0へ変換 |
| アラーム オン/オフ | なし | 元情報のみ保存。通知しない |
| アラーム日付 | なし | 元情報のみ保存 |
| アラーム時刻 | なし | 元情報のみ保存 |
| 会議の開催者 | なし | 元情報のみ保存 |
| 必須出席者 | なし | 元情報のみ保存 |
| 任意出席者 | なし | 元情報のみ保存 |
| リソース | なし | 元情報のみ保存 |
| プライベート | なし | 元情報のみ保存。予定別の権限制御には使用しない |
| 経費情報 | なし | 元情報のみ保存 |
| 公開する時間帯の種類 | なし | 元の値のみ保存。予定表示の制御には使用しない |
| 支払い条件 | なし | 元情報のみ保存 |
| 場所 | `location` | 表示・編集・検索対象 |
| 内容 | `body` | 表示・編集・検索対象。複数行を保持 |
| 秘密度 | なし | 元情報のみ保存。予定別の権限制御には使用しない |
| 分類 | `categories` | 表示・編集対象。現在の検索対象には含めない |
| 優先度 | なし | 元情報のみ保存。並び順には使用しない |

必須列は件名・開始日・開始時刻・終了日・終了時刻・終日イベント。場所・内容・分類がないCSVでは、通常項目に空文字を入れる。CSVにない列を移行元JSONへ補って追加する処理はない。

元CSVの項目は予定編集時に書き換えない。現在の件名等と移行元の件名等が異なる状態は正常である。

## 7. 日時・終日予定・日別一覧

通常の予定は「開始を含み、終了を含まない」期間として日別一覧へ表示する。

| 例 | 保存値 | 日別一覧での表示 |
|---|---|---|
| 10月9日の終日予定 | 開始`2026-10-09T00:00:00`、終了`2026-10-10T00:00:00`、終日1 | 10月9日のみ |
| 10月9日～11日の終日予定 | 開始10月9日0時、終了10月12日0時、終日1 | 9日・10日・11日 |
| 10月9日23時～10日1時 | 開始9日23時、終了10日1時、終日0 | 9日・10日 |
| 10月9日23時～10日0時 | 開始9日23時、終了10日0時、終日0 | 9日のみ |
| 開始・終了が同時刻 | 両方同じ日時、終日0 | 開始日のみ |

入力画面での終日予定の終了日は「最終日」。保存時に翌日0時へ変換する。Outlook CSV取込では終了日時をそのまま保持し、余計に1日を加算しない。

新規登録・編集では、終了が開始より前の場合は拒否する。終日予定は開始・終了が0時、終了が開始より後であることを要求する。空の件名は許容し、画面では「（件名なし）」と表示する。

日別一覧は終日予定を先にし、次に開始日時、IDで並べる。入力画面・日付移動では9999-12-31を指定対象から除外している。

## 8. 検索

- 対象は現在の`subject`・`location`・`body`。分類・元CSV情報は対象外。
- NFKC正規化と`casefold()`で、全角・半角、英字の大文字・小文字等の差を吸収する。
- 空白区切りはAND検索。すべての語が、いずれかの対象項目に含まれる予定を返す。
- 一つの語が項目の境界をまたいで一致することはない。
- 空の検索語は0件を返す。
- `%`・`_`・引用符は普通の検索文字として扱う。
- 結果は開始日時、終日優先、IDの順。削除済みは除外する。
- 正規化済み文字列の専用列や全文検索テーブルはなく、検索時の関数で照合する。

## 9. 新規登録・編集・削除

| 操作 | events | 移行元情報・取込履歴 |
|---|---|---|
| CSV取込 | 各レコードを新しい予定として保存 | 元項目・行番号・取込IDを保存 |
| 新規登録 | 通常項目を保存、`is_deleted = 0` | 移行元3項目はNULL、取込履歴は作らない |
| 編集 | 件名・日時・終日・場所・内容・分類を更新 | 元項目・行番号・取込IDは保持 |
| 削除 | `is_deleted = 1`へ更新 | 予定本体・元情報・履歴を保持 |

削除済み予定は日別一覧・検索・通常の詳細取得から除外する。編集も拒否する。存在しない予定や削除済み予定をもう一度削除する場合はエラーにする。

復元画面・復元処理・完全削除は現在未実装。作成日時・更新日時・削除日時、編集履歴の保存も未実装。

## 10. トランザクションと取込エラー

CSV全体の形式・日時を確認してから、取込履歴と予定を一つのトランザクションで保存する。途中の保存失敗時は、その取込をすべてロールバックする。

取込は`BEGIN IMMEDIATE`で開始し、同一取込の存在確認と保存をまとめて行う。取込・構造更新・登録・編集・削除の入口では、呼び出し元の未確定トランザクションがある場合に拒否する。

列不足・列過多・重複列名・不正な日時・不正な終日指定等は読取エラー。CSVのレコード番号は、内容内の改行を含めたファイル上の物理行番号とは異なる。

## 11. DB識別・構造更新

| 管理値 | 設定 | 用途 |
|---|---|---|
| `PRAGMA application_id` | `0x43444B31`（1128549169） | CalendarDockのDB識別 |
| `PRAGMA user_version` | 現在3 | DB構造バージョン |
| `app_metadata.application` | `CalendarDock` | 管理情報による識別 |
| `PRAGMA foreign_keys` | 接続ごとにON | 参照整合性の有効化 |

| バージョン | 構造・更新内容 |
|---|---|
| 1 | 基礎DBを作成。CSV取込時に取込履歴・予定テーブルを作成。移行元3項目は必須 |
| 2 | 予定テーブルを作り直し、新規予定では移行元3項目をNULLにできる。未取込DBにも予定テーブルを整備 |
| 3 | `is_deleted`を追加。既存予定の初期値は0 |

`upgrade_database()`は1→2、`upgrade_for_deletion()`は2→3を担当する。それぞれ対応する更新済みバージョンでは変更せず終了する。`upgrade_database()`はバージョン3には対応していないため、3へ更新したDBに1→2の更新スクリプトを再実行しない。

`open_database()`は1・2・3の識別・接続に対応する。現在の起動画面は、登録・編集・削除が使えるバージョン3だけを通常利用の対象として開く。旧DBの自動更新は起動画面では行わない。

## 12. 暗号化・バックアップ・検証

パスワード設定後にスキーマを読み、復号して開けることを確認する。誤パスワード・破損・形式不一致を、復号失敗だけから厳密に区別することはできない。標準の`sqlite3`では暗号化DBを読めないことをテストしている。

| 確認 | 正常時の結果 |
|---|---|
| `PRAGMA integrity_check` | `ok` |
| `PRAGMA cipher_integrity_check` | エラー行なし |
| `PRAGMA foreign_key_check` | 不整合行なし |
| 接続を閉じて再度開く | 同じパスワードで内容を取得できる |

現在のバックアップ運用は、アプリを終了した状態でDBファイルをコピーする方式。コピーも暗号化されており、同じパスワードで開く。稼働中DBの単純なファイルコピーはこの運用の対象外。

元CSVは暗号化されていない別ファイルであり、取込後にDBと一体化して暗号化されるわけではない。Git管理ではCSV・DB・バックアップを除外する。

## 14. 件数を確認するSQL

以下は、パスワードで開いたSQLCipher接続で実行する。バージョン3を対象とする。

```sql
-- 保存されている全予定数（削除済みを含む）
SELECT count(*) FROM events;

-- 通常表示する予定数
SELECT count(*) FROM events WHERE is_deleted = 0;

-- 削除済み予定数
SELECT count(*) FROM events WHERE is_deleted = 1;

-- CSV由来の予定数（削除済みを含む）
SELECT count(*) FROM events WHERE import_batch_id IS NOT NULL;

-- CalendarDockで新規登録した予定数（削除済みを含む）
SELECT count(*) FROM events WHERE import_batch_id IS NULL;

-- CSV取込履歴
SELECT id, source_name, imported_at, event_count
FROM import_batches ORDER BY id;
```

通常表示件数は全予定件数から削除済み件数を除いた値。取込履歴の件数合計は新規登録分を含まないため、全予定件数と必ずしも一致しない。
